# Binary Frames & Floor Control

A way to send data at a media rate, and — when the application needs it — a way
to decide who is allowed to. Konet arbitrates who may send; it never looks at
what is sent.

## Binary modes

A topic runs one of two modes, chosen at join:

| Mode | Who may send | For |
|------|--------------|-----|
| `exclusive` (default) | the floor holder only | half-duplex: push-to-talk, a radio net, a turn-taking game — a second sender must be *told no* rather than mixed in |
| `multiplex` | every member, at any time | full-duplex: a call, where both sides talk at once |

```js
// push-to-talk: nothing to ask for, exclusive is the default
const ptt = client.channel('room:team-42:ptt')

// a call
const call = client.channel('room:call-7', { binaryMode: 'multiplex' })
await call.subscribe()
call.sendBinary('a', frame) // no floor to take
```

**The mode belongs to the topic.** A push-to-talk client relies on a second
sender being refused, and a call client on never being refused, so they cannot
share one. The first member fixes the mode; a joiner asking for the other one is
refused, and told which mode is in force:

```json
{ "status": "error", "response": { "reason": "binary_mode_mismatch", "binary_mode": "multiplex" } }
```

Every member of a multiplex topic — including one that only sends text — must
therefore join with `binaryMode: 'multiplex'`. The mode is forgotten once the
last member leaves.

The join reply confirms the mode, readable as `channel.binaryMode` once joined.
A server older than modes confirms nothing; the SDKs read that as `exclusive`,
which is all it ever did.

## Floor control

In `exclusive` mode only. At most one member of a topic holds the floor at a
time.

```js
const channel = client.channel('room:team-42:ptt')
await channel.subscribe()

try {
  await channel.acquireFloor()
  // you may now send binary frames
} catch (error) {
  // someone else is talking; the error names them
}

await channel.releaseFloor()
```

Everyone on the topic — including the holder — receives an announcement, so a
UI can show who is talking without asking:

```js
channel.on('konet:floor', ({ holder }) => {
  // holder is a user id, or null when the floor is free
})
```

### Guarantees

**Acquisition is atomic.** Two clients pressing in the same millisecond resolve
to one winner. The floor lives in a single ETS table and is claimed with a
compare-and-swap, so there is no window where both believe they hold it.

**A repeated acquire by the holder succeeds.** A client that presses twice, or
retries after a slow reply, is not punished for it.

**Only the holder can release.** A late release from a previous holder cannot
cut off whoever is talking now.

**The floor is always freed.** Three separate paths cover it: an explicit
release, the holder's channel process dying — a rider entering a tunnel
mid-sentence — and a sweep for holders that exceed `KONET_FLOOR_MAX_HOLD_MS`
(default 30 000). A client that vanishes cannot mute a channel. Every one of
these paths announces `konet:floor` with `holder: null`, the holder included —
which is how a holder whose floor expired finds out.

### Refusals

```json
{ "status": "error", "response": { "reason": "floor_held", "holder": "alice" } }
{ "status": "error", "response": { "reason": "not_holder" } }
```

On a `multiplex` topic the floor does not exist — it is not granted to everyone,
it is never consulted. Both floor events are refused, and no `konet:floor` is
ever announced:

```json
{ "status": "error", "response": { "reason": "floor_disabled", "binary_mode": "multiplex" } }
```

## Binary frames

Phoenix carries binary payloads in their own framing rather than base64 inside
JSON. At 50 frames a second — 20 ms of Opus — that difference is a third of the
bandwidth and a JSON parse per frame.

```js
channel.on('a', (data) => {
  // data is a Uint8Array
})

await channel.acquireFloor()
channel.sendBinary('a', frame)
```

The event name is yours; short is better, since it travels on every frame.

### Rules

**In `exclusive` mode, the floor is required.** A binary frame from a client
that does not hold it is refused with `floor_required`. In `multiplex` mode any
member may send; frames from several members are relayed independently, none
waits for or replaces another.

**In `multiplex` mode, every frame names its sender.** The server puts the
sender's user id — the token's `sub` — in front of the data before relaying it,
and the SDKs split it off and hand it to the handler:

```js
call.on('a', (data, sender) => {
  decoders.get(sender).decode(data) // one stream per sender
})
```

The server writes it, so a member cannot pass for another. A member whose user
id is longer than 255 bytes cannot be carried by the one-byte length and is
refused at a multiplex join with `invalid_sender_id`. In `exclusive` mode frames
are relayed untouched: the floor holder is the sender.

**Frames are never echoed to the sender.** Konet uses `broadcast_from!`, not
`broadcast!` — returning a talker's own audio is echo, and on a phone it is echo
at speaker volume.

**Frames are not acknowledged.** At a media rate a reply per frame would cost
more than the frames do. Only a refusal comes back.

**Frames are not recorded in history.** Buffering 50 frames a second would blow
up the replay buffer for a replay nobody can use. Recording media is a durable
storage problem, not a replay-buffer one.

**Frames are not buffered across a reconnect.** A client SDK drops binary frames
while the socket is down rather than queueing them. Replaying audio recorded
seconds ago into a live channel is worse than losing it — by the time it
arrives, the moment has passed.

### Rate limiting

Binary frames have their own budget, `KONET_RATE_LIMIT_BINARY` (default 120 per
second per socket), separate from the message budget. They arrive at a media
rate, not a message rate: 20 ms frames are 50 per second on their own, and
sharing the message budget would have a talker starve their own position
updates.

The limit is per socket: it stops one client flooding. In `exclusive` mode the
floor also bounds a topic to one sender; in `multiplex` mode nothing does, so
a topic with *n* senders fans out *n × (n − 1)* streams.

## Performance

Binary broadcasts take Phoenix's *fastlane*: the frame is encoded once and
written to every subscriber's socket without passing through their channel
processes.

The hot path does nothing else — no history, no per-frame logging. Those were
removed deliberately, and audio is where their cost would first show.

## Wire format

You do not need this to use the SDKs, which implement it. It is here so a
client in a language Konet does not ship can be written, and so the framing can
be verified during an audit.

Three shapes, told apart by the first byte. Every size field is one byte, so
each field is capped at 255 bytes.

```
push       0 | join_ref_size | ref_size | topic_size | event_size | join_ref | ref | topic | event | data
reply      1 | join_ref_size | ref_size | topic_size | status_size | join_ref | ref | topic | status | data
broadcast  2 | topic_size | event_size | topic | event | data
```

The directions are **not** symmetric: a client-to-server push carries a `ref`,
a server-to-client push does not. This is Phoenix's choice, and it is the
mistake to expect when writing a new client — the SDKs name their decoders
`decodeServerFrame` rather than `decodeFrame` for exactly that reason.

Sizes are byte counts, not character counts. A topic like `room:équipe` is 11
bytes for 10 characters; using the character count shifts every field after it.

On a `multiplex` topic, the `data` of a frame received from the server is
itself prefixed with its sender:

```
data       sender_size | sender | payload
```

`sender_size` is one byte, `sender` is the sender's user id in UTF-8, `payload`
is what the sender sent. A client sends its frames without this prefix; only the
server adds it. `exclusive` frames have no prefix.

## Configuration

| Variable | Default | Purpose |
|----------|---------|---------|
| `KONET_RATE_LIMIT_BINARY` | `120` | Binary frames per second, per socket |
| `KONET_FLOOR_MAX_HOLD_MS` | `30000` | Before a stuck holder is swept |

## Support by SDK

| SDK | Mode | Binary | Floor |
|-----|------|--------|-------|
| JavaScript | `client.channel(topic, { binaryMode })` | `channel.sendBinary()` / `channel.on(event, (data, sender) => …)` | `acquireFloor()` / `releaseFloor()` |
| React Native | same, via the JavaScript core | same | same |
| Go | `client.Channel(topic, konet.WithBinaryMode(konet.BinaryMultiplex))` | `channel.SendBinary()` / `channel.OnBinary()`, or `channel.OnBinaryFrom()` for the sender | `AcquireFloor()` / `ReleaseFloor()` |
| Python | `client.channel(topic, binary_mode="multiplex")` | `channel.send_binary()` / `channel.on_binary()`, or `channel.on_binary_from()` for the sender | `acquire_floor()` / `release_floor()` |

The SDKs send the mode on every join, reconnects included.

React Native needs no native module: its WebSocket supports
`binaryType = "arraybuffer"`, so binary frames work on a phone exactly as they
do in a browser.
